# Accessibility Check - Mira Marketplace

Audit date: 2026-06-25  
Scope: Static source review, lecture material review from `docs/context`, and existing automated accessibility tests.  
Verification run: `npm run test:a11y` passed with 106/106 tests.

This document is written as an engineering handoff for junior developers. It explains not only what to change, but also why the issue matters, which lecture concept it comes from, what the current implementation does, and what risk that creates for users.

## Fix These Next

| Priority | Finding | Lecture reference | Current implementation | Why this is a problem | User impact | Fix direction |
| --- | --- | --- | --- | --- | --- | --- |
| High | Skip link target is missing on some pages | `Semantisches HTML.pdf`: landmark regions and `<main>`; `03_AssistiveTechnologien.pdf`: keyboard navigation; WCAG 2.4.1 Bypass Blocks | `Navbar` provides a skip link to `#main-content`, but at least `BookingPage`, `CalendarPage`, and `PaymentReturnPage` render `<main>` without `id="main-content"` (`BookingPage.tsx:264`, `CalendarPage.tsx:226`, `PaymentReturnPage.tsx:20`). | A skip link only works if the target exists. Without the target, keyboard and screen-reader users still have to move through repeated navigation before reaching the page content. This defeats the purpose of the bypass mechanism. | Keyboard-only users, switch users, and screen-reader users lose a fast path to the main task. This is especially painful on task pages like booking and calendar. | Add `id="main-content"` to every routed `<main>` rendered with `Navbar`. Add a small test that each page with `Navbar` exposes a matching skip target. |
| High | Booking-page validation is partly visual only | `Semantisches HTML.pdf`: accessible forms and error messages; WCAG 3.3.1 Error Identification and 3.3.2 Labels or Instructions | The booking description field changes border/text styling when shorter than 10 characters, but it does not set `aria-invalid`, and the blocking message is only part of hint text (`BookingPage.tsx:581-610`). | Screen readers do not reliably infer that a field is invalid from CSS. If the form blocks submission, the invalid control and reason need to be programmatically exposed. The project already does this well in `Input` and `Textarea`; this custom textarea should follow the same pattern. | Screen-reader users may submit, hear nothing useful, and not know which field prevents progress. Users with cognitive load also benefit from explicit, consistent error wording. | Add `aria-invalid` when the field is invalid, connect the specific error with `aria-describedby`, and use `role="alert"` or a consistent live-region pattern when validation blocks submission. Consider reusing the existing `Textarea` component. |
| High | Custom ARIA listbox/radio patterns need interaction review | `ARIA.pdf`: ARIA should match widget behavior; `03_AssistiveTechnologien.pdf`: keyboard navigation; WCAG 2.1.1 Keyboard and 4.1.2 Name, Role, Value | Booking time slots use `role="listbox"` and child buttons with `role="option"`. Location and registration role choices use button-based `role="radio"` patterns (`BookingPage.tsx:382-443`, `BookingPage.tsx:519-571`, `RegisterRole.tsx:69`). | ARIA roles are a contract. If an element says it is a listbox or radio group, users expect the keyboard model for that widget, often including arrow-key movement and predictable selection behavior. Native controls provide this for free; custom widgets must implement it deliberately. | Screen-reader and keyboard users may hear a familiar role but get unfamiliar behavior. This creates confusion and can make the booking flow feel broken even when clicking works. | Prefer native radio inputs for single-choice groups. For time slots, either use plain buttons without listbox semantics or implement a complete listbox pattern with roving focus and arrow keys. |
| High | Booking and calendar need manual reflow testing | `Wahrnehmbarkeit.pdf`: distinguishable/adaptable content; `06_Design.pdf`: inclusive responsive design; WCAG 1.4.10 Reflow and 1.4.4 Resize Text | `BookingPage` uses horizontal layouts plus a fixed bottom summary. `CalendarPage` uses a wide calendar and a side panel (`BookingPage.tsx:331`, `BookingPage.tsx:511`, `BookingPage.tsx:612`, `CalendarPage.tsx:269`). | Axe tests can pass while a layout still fails at 320 px width, 200% zoom, or browser text zoom. Reflow is about whether users can read and operate content without two-dimensional scrolling or hidden controls. | Low-vision users, mobile users, and users who zoom text may lose access to the submit button, calendar details, or time-slot controls. | Manually test 320 px width, 200% zoom, and text zoom. Stack columns, avoid fixed overlays covering content, and ensure the bottom booking bar does not obscure focus or content. |
| Medium | Page title is static | `Semantisches HTML.pdf`: `<title>` must be present, short, consistent, and describe page content; WCAG 2.4.2 Page Titled | `index.html` defines only `<title>Mira</title>`, and route-specific title updates were not found (`index.html:10`). | A static title gives no context when users switch tabs, navigate browser history, bookmark pages, or use a screen reader's page summary. A marketplace has many task pages, so the page title should identify the current task. | Screen-reader users and keyboard users who rely on browser/tab context may not know whether they are on search, booking, calendar, credentials, or payment status. | Add route-specific titles such as `Browse Services - Mira`, `Book Service - Mira`, `My Calendar - Mira`, and `Payment received - Mira`. |
| Medium | Accessibility statement is informative but not formal enough | `04_RechtlicheGrundlagen.pdf`: accessibility statement must describe current status, open problems, contact, and update date | The `Accessibility at Mira` page explains accessibility features and contact information, but does not include conformance status, known inaccessible parts, enforcement/feedback path, or last-updated date (`infoPages.ts`). | The lecture distinguishes general accessibility information from an accessibility statement. A statement is an accountability document: it tells users what works, what does not, and how to report barriers. | Users encountering a barrier may not know whether the team is aware of it, how to report it, or when the statement was last reviewed. | Add sections for conformance status, known issues, inaccessible content, feedback contact, expected response path, and last updated date. Keep the statement itself accessible. |
| Medium | Low-opacity text on gradients and muted surfaces needs contrast measurement | `Wahrnehmbarkeit.pdf`: distinguishable content; WCAG 1.4.3 Contrast Minimum and 1.4.11 Non-text Contrast | Several UI areas use low-opacity foreground colors such as `text-cream/60`, `text-primary-foreground/60`, and muted text over tinted or gradient backgrounds. | Contrast cannot be judged reliably from design tokens alone, especially when opacity and gradients are involved. Text that looks subtle to one user can become unreadable for low-vision users or in bright environments. | Low-vision users, older users, and users on poor displays may miss status hints, explanatory copy, or secondary labels. | Measure actual rendered foreground/background combinations with a contrast checker. Raise opacity or choose stronger colors where ratios fail. |
| Medium | Dynamic status announcements are inconsistent | `AccessibilityTree.pdf`: events/notifications; `03_AssistiveTechnologien.pdf`: screen readers react to focus and events; WCAG 4.1.3 Status Messages | Loading and error states are often exposed, but success messages, filter-result changes, booking state changes, and some calendar updates are not consistently announced with `role="status"` or `aria-live`. | If content changes without focus moving, screen readers may not announce it unless the change is exposed as a status message. Visual users see counts and cards update; non-visual users need an equivalent notification. | Screen-reader users may not know that a search completed, filters changed the result count, a booking request was sent, or calendar data refreshed. | Standardize a `StatusMessage`/live-region pattern for async updates that do not move focus. Use polite announcements for non-urgent updates and alerts for errors. |
| Medium | AI-generated alt text needs human review | `Wahrnehmbarkeit.pdf`: text alternatives and AI caveat; WCAG 1.1.1 Non-text Content | `ServiceCard` uses generated alt text when `pictureAltTextStatus === 'COMPLETED'`, otherwise it falls back to the service title (`ServiceCard.tsx:78-81`). | The architecture is good, but the lecture explicitly notes that AI alt text can be inaccurate and context-dependent. Alt text must describe the image's purpose in this exact listing context, not just what an image model guessed. | Screen-reader users may receive misleading service information if the generated text is wrong, too generic, or misses important context. | Keep the fallback, but add provider/admin review of generated alt text for important service images. Consider allowing providers to edit alt text. |

## Implemented Well

| Component / Pattern | Lecture reference | What you did well | Why it matters |
| --- | --- | --- | --- |
| Automated accessibility tests | WCAG practice and quality assurance across lectures | `npm run test:a11y` runs axe checks across many component states and currently passes 106/106 tests. | This catches regressions in names, roles, labels, dialog states, and many structural issues before manual review. It is a strong habit for a student project. |
| Global focus styling | `03_AssistiveTechnologien.pdf`: keyboard navigation; WCAG 2.4.7 Focus Visible | `globals.css` defines visible focus styling and components add focus rings where needed. | Keyboard users need to know where they are. A visible focus indicator is one of the most practical accessibility wins. |
| Reduced motion support | `06_Design.pdf` and perceivability/operability principles | The app respects `prefers-reduced-motion` and also exposes an in-app reduced-motion setting. | Users with vestibular disorders or concentration needs can reduce animation without losing functionality. |
| Reusable `Input` and `Textarea` components | `Semantisches HTML.pdf`: forms and validation | These components connect errors through `aria-invalid`, `aria-describedby`, and `role="alert"`. | Junior developers can reuse these primitives and get accessible error handling by default. This reduces one-off mistakes. |
| Dialog and popover handling | `ARIA.pdf`; `AccessibilityTree.pdf`: roles, states, names, focus | The modal uses dialog semantics, labelled title, escape handling, focus movement, and focus return. Popovers and Radix dialogs show similar intent. | Dialogs are high-risk because they interrupt focus. Your implementation shows awareness of focus management and screen-reader semantics. |
| Navigation structure | `Semantisches HTML.pdf`: landmarks; `03_AssistiveTechnologien.pdf`: screen-reader navigation by landmarks/headings | The navbar uses a real `nav`, has an accessible label, and includes a skip link. Most pages use `<main>`. | Landmarks help screen-reader users understand page structure and move quickly. Once the missing targets are fixed, this becomes a strong pattern. |
| Image handling | `Wahrnehmbarkeit.pdf`: text alternatives; `Content Hiding.pdf`: decorative content | Decorative logos can be hidden with empty alt text, avatars have fallback names, and service images track alt-text generation status. | The team is distinguishing decorative, functional, and informative images instead of treating every image the same. |
| Accessibility as a product feature | `02_WasIstBarrierefreiheit.pdf`: accessibility benefits all users; inclusive design | The accessibility panel, easy-language option, reduced-motion setting, contact page, and public accessibility page make accessibility visible in the UI. | This supports users before they are blocked, and it signals that accessibility is part of the product rather than a hidden technical checkbox. |

## Biggest Blunders / Urgent Manual Review

| Area | Why this is urgent | What to test manually | What a good result looks like |
| --- | --- | --- | --- |
| Booking page | It is a critical transaction flow. If this flow is inaccessible, users cannot complete the core marketplace task. | Keyboard-only booking from start to submit; screen-reader announcement of selected date/time/location; validation errors; 320 px width; 200% zoom; fixed bottom bar. | A user can book without a mouse, understands every selected value, hears errors clearly, and never loses controls behind the fixed footer. |
| Calendar page | It is dense, stateful, and visually encoded with date cells, badges, legends, and side panels. | Keyboard traversal, day labels, booking/blocked/available states, legend meaning, zoom/reflow, and non-color cues. | A user can understand each day state from text, not color alone, and can operate calendar actions without layout breakage. |
| Accessibility statement | It is currently a friendly explainer, not a formal statement. | Presence of conformance status, known issues, feedback mechanism, last updated date, and reachable link from every page. | A user can understand the current accessibility status and report a barrier through a clear process. |
| Custom ARIA controls | These are the places where automated tests most often miss human usability problems. | Every `radiogroup`, `listbox`, `switch`, popover, and card-as-group pattern with Tab, Shift+Tab, Enter, Space, Escape, and arrow keys. | Roles and keyboard behavior match user expectations. If they do not, use native controls or simpler semantics. |
| Responsive/high-zoom layouts | Visual density can break accessibility even when semantics are correct. | 320 px viewport, 200% zoom, browser text zoom, long labels, and reduced motion. | Content reflows in one direction, text remains readable, focus is visible, and no control is hidden or overlapped. |

## Suggested Manual Test Matrix

| Test type | How to test | Why it matters |
| --- | --- | --- |
| Keyboard only | Use Tab, Shift+Tab, Enter, Space, Escape, and arrow keys. Do not touch the mouse. | This reveals focus traps, missing focus states, wrong custom-widget behavior, and unreachable actions. |
| Screen reader | Prefer NVDA + Chrome/Firefox on Windows if available. Also test VoiceOver + Safari on macOS. | Different browser/screen-reader pairs expose different accessibility tree behavior. |
| Zoom and reflow | Test 200% browser zoom and a 320 px viewport. Also try text zoom if the browser supports it. | Low-vision users often zoom. Layouts must remain usable without horizontal scrolling or occlusion. |
| Contrast | Measure actual rendered colors, especially opacity text and gradients. | Design tokens can pass in isolation while the rendered combination fails. |
| Reduced motion | Test OS-level reduced motion and the in-app reduced-motion toggle. | Motion preferences should reduce animation without removing information or functionality. |
| Content hiding | Open/close file inputs, popovers, dialogs, drawers, and hidden panels. Check that invisible controls are not focusable. | Hidden interactive content can create confusing focus stops or screen-reader noise. |
| Dynamic status | Trigger search, filtering, loading, validation, booking submission, calendar changes, and save/publish flows. | Screen-reader users need equivalent feedback when the UI changes without a page reload. |

## Notes For The Team

- Passing automated tests is a strong signal, not a full accessibility guarantee. Your remaining risks are mostly route-level behavior, custom interaction models, content quality, and manual assistive-technology behavior.
- When choosing between native HTML and ARIA, prefer native HTML unless the custom interaction is truly needed. Native controls already bring keyboard behavior, semantics, and state exposure.
- When a visual state blocks progress, make it programmatic too. A red border is not enough; pair it with `aria-invalid`, linked error text, and a status/alert pattern where appropriate.
- When a page is important to the business flow, test it manually even if axe passes. Booking and calendar deserve the deepest manual pass.
